The package-free starter graph created by `isos config init` contains three cores and 17 nodes. Its IsOS button passes an activation through EI input, cognition, and safety, then EOS ingress, demo skill, dispatcher, and mock six-joint arm. A read-only observation path returns the arm state through EOS and EI to the IsOS monitor and feeds the EI context node. The optional [mixed example](../../../examples/mixed-mujoco.nodes.json) adds a package camera, EOS vision flow, and UI vision monitor; it has 17 nodes, intentionally leaves the control path without an activation source, and requires the verified `island/mujoco-sim@0.2.4` release and its configuration before Apply.

1. Build IsOS, `aether-profile`, and `aether-runtime`, and install the EI programs from `ei/pyproject.toml`. Set `ISOS_AETHER_BIN_DIR` and `ISOS_EI_BIN_DIR` to the selected executable directories.
2. Run `isos config init`. It saves the package-free starter at the selected IsOS home under `config/graph-pool/demo.nodes.json`; the deployment stores only its pool-name binding. The repository [demo graph](../../../config/graph-pool/demo.nodes.json) extends that starter with a native MuJoCo camera, EOS vision flow, and UI vision monitor. To use it, install or link the verified `island/mujoco-sim@0.2.6` release, import its required configuration, and copy the repository demo into that home pool file before validation and Apply. The separate [mixed example](../../../examples/mixed-mujoco.nodes.json) uses `0.2.4` and has no activation source.

3. Validate and Apply that pool file. Apply requires its exact-byte SHA-256 through `--revision`; `config apply --file` accepts only a file in the graph pool.
4. Open the workbench with `isos web` (or `isos serve` for a foreground server). IsOS starts persistent EI and EOS owner services in the background and shows their initial connection status while their inner catalogs load; it does not start deployment workers. Moving nodes changes only the browser's saved canvas layout. When ready to execute, use **Save and Run** in the workbench or explicitly run `isos start` / `isos run`. Then read `isos status --json`: EI should report `running`, EOS `ready`, and the EOS mock adapter `ready`.
5. With the package-free starter graph, click **Activate** on the button node in the workbench, or use `isos demo activate demo-1`, `isos demo result demo-1`, and `isos demo monitor` for a CLI-only replay. The mixed example has no button activation source, so its incomplete control path remains inactive. The button first shows an accepted event ID, then reads the correlated result separately; each distinct accepted activation moves the mock arm by a small fixed joint delta when it succeeds. Inspect the final positions, the independent arm monitor snapshot, and owner logs. Then run `isos deployment stop` to stop both deployment workers; the owner services remain available for setup and a later Run. Press Ctrl+C to close a foreground `isos run` session. `isos stop` invokes the workspace emergency stop using the configured code.

An existing home graph is never overwritten by `config init`. To migrate an older `demo` pool file, back it up, replace it with the repository demo after installing its pinned package, or create **New graph** in the editor and save it, then validate and Apply the new exact revision.

The repository demo pins `island/mujoco-sim@0.2.6` for both the camera type and adapter. Its native front camera requests 1280×720 pixels at 30 Hz and declares JPEG capability. The camera emits JPEG directly from the selected MuJoCo scene; this graph is not a RoboCasa camera preset.

An isolated local strict-socket source probe on 2026-11-17 returned 31 distinct 1280×720 JPEG capture timestamps in 0.88–1.07 seconds across runs (28–34 fresh FPS). Reproduce with the native package's `tests/vision_rate.py` in the MuJoCo source worktree. A separate isolated EOS-to-WebSocket run delivered 72 distinct frames over 3.115 seconds (22.79 FPS). Thus 30 Hz is the requested capture and transfer rate, not a measured end-to-end guarantee on this host. The Vision page reports its observed delivered FPS during a running deployment.

If validation reports `generated_missing_input`, its stage now appears in parentheses. The `binary` stage checks selected owner executables and EI source files; an optional EI source directory containing only ignored bytecode no longer blocks the graph. To reproduce the load check, run `./isos.sh config validate config/graph-pool/demo.nodes.json` from the repository root. On 2026-11-16, this command returned `valid node graph` after the empty-directory fix, and `ISOS_AETHER_BIN_DIR=$PWD/target/debug RUST_TEST_THREADS=1 cargo test -p isos --offline`, the focused regression test, formatter, and strict IsOS Clippy passed. Output is under ignored `data/test/20261116-demo-load/checks.log`. On 2026-11-17, the camera frequency editor and camera source lookup were checked with `ISOS_AETHER_BIN_DIR=$PWD/target/debug RUST_TEST_THREADS=1 cargo test -p isos --offline`, `./isos.sh config validate config/graph-pool/demo.nodes.json`, and from `ui/`, `npm run typecheck`, `npm test`, `npm run build`, and `npm run build:tui`. All passed; full outputs are under ignored `data/test/20261117-camera-frequency/`.

After changing a selected core binary, Apply the graph again before Run to refresh the verified launch-input digest. IsOS can exit while EI and EOS owners keep running; restart IsOS and read status to reattach by the retained run identity. The workbench log section replays selected owner startup and runtime records from IsOS's durable pools. A failed owner is reported separately while the healthy owner remains live. See the [runtime design and replay](../core/server.md) and [graph API](../interfaces/api/http.md#http_graph).

For a package with a configuration descriptor, open **Runtime overview → Package configuration** in the Web workbench. Choose the exact installed package version, edit the described fields or switch to the raw TOML view, then **Validate** and **Save configuration**. The panel opens automatically when only one configurable package is installed. Saving changes the local configuration revision; Apply the selected graph again before Run.

To add package nodes, install or link the exact release first, then choose its registered type in the node library or preview its node set. A package type appears under its declared core, layer, and group; the saved instance receives a top-level `package` pin. For a new hardware node, choose its adapter family, then fill the required device fields and service instance. The workbench can show verified catalog choices while the draft is incomplete; EOS checks the finished draft before Apply. Choosing a package adapter sets its exact `adapter.package` pin. Apply rejects a missing type declaration or changed package bytes. The older MuJoCo v0.2.1 release does not declare its hardware types; use a qualified later release for the package-owned hardware path.

To check updates for packages already installed locally, run `isos pkg update`. It checks only those package IDs for newer approved, contiguous patches in the installed major/minor line; it does not download them. Use `isos pkg install` for a different version line or across a missing patch. Run `isos pkg upgrade <namespace/name>` for one listed package, or `isos pkg upgrade` for all listed packages. Confirm each exact asset preview when prompted. The verified new version is installed beside the old one; edit the graph's `package` and `adapter.package` pins where applicable, validate, and Apply before using it in a later Run. If the installed inventory changed after the update check, run `isos pkg update` again. Product updates use the separate `isos update` and `isos upgrade` commands.

If a newer package exists only as a local checked candidate, it will not appear in `pkg update` until its exact version is published in the approved catalog. Publishers must release contiguous checked patches: when the latest published version is `0.2.1`, qualify and publish `0.2.2` before `0.2.3`, each with its own matching immutable tag and qualification. See the [package publication contract](../interfaces/package/README.md#package-admission-and-publication-rules). Installing either version still leaves the graph's exact pin unchanged.

Use `isos web` when editing the graph without running the deployment. `isos run` is a foreground command that explicitly starts both deployment workers; ending its terminal session also ends that workbench server. A detached `isos web` server remains available while the graph is edited. For a CLI-only replay, use `isos run --no-ui`: it starts the manager, local API, and deployment without opening a browser or starting a UI listener. `isos serve --no-ui` starts only the manager and API; then use `isos start` to run the applied graph. The headless button event and monitor requests use the same [local HTTP API](../interfaces/api/http.md) as the workbench.

## EI preparation and diagnostics

The product installer `./install.sh` builds and installs EI with IsOS and EOS. To build only the EI wheel, run `./scripts/ei/platform/dispatch.sh build` from the repository root. Authored EI TOML lives in `config/ei/`, factory defaults in `config/defaults/ei/`, and installed configuration in `etc/ei/` and `etc/island.toml`. `EI_ETC` or `ei/bin/ei --etc <path>` selects another configuration root; `--mode` selects a mode from `config/ei/modes.toml` for that invocation. Keep API keys in the ignored repository-root `.env` or exported variables; [`.env.example`](../../../.env.example) lists names only, and process variables take precedence. Credentials do not belong in TOML or logs.

IsOS selects the EI programs, sends a bounded setup request to `ei-config`, and supervises the runtime. The managed setup accepts only the isolated EI projection; setup health alone does not prove EI or EOS readiness. For a source diagnostic outside a managed run, use `ei/bin/ei --mode sandbox` from the repository root. `--managed` is reserved for IsOS and rejects an internally launched sandbox. The launcher options are in `ei/bin/ei --help` and `ei/bin/ei-config --help`; the [EI setup](../interfaces/server/ei.md#setup) and [runtime](../../ei/interfaces/server.md#runtime) contracts own wire details.

Standalone EI diagnostics are in `data/ei/log/local/ei.jsonl`; managed runs use `data/ei/log/<deployment>/ei.jsonl`. IsOS reads this local file for its log panel, while EI owner replies carry lifecycle state rather than logs. `EI_LOG_DIR` and `EI_DEPLOYMENT` select a private diagnostic root and deployment. A bounded local check is `timeout 8s ei/bin/ei --mode sandbox`, followed by `tail -n 30 data/ei/log/local/ei.log`. If EOS discovery is missing or partial, inspect EOS health and EI link diagnostics before retrying; EI needs a complete generation to admit commands. Optional model, recall, or skill degradation never relaxes safety. Back up `data/ei/state/` and user files; clear cache or temporary files only after EI stops.

For EI development, run `uv sync --extra dev --extra vec` in `ei/`, then `uv run ruff check .`, `uv run pyright`, `PYTHONPATH=.:package uv run lint-imports --cache-dir ../data/cache/tools/import-linter-ei`, and focused or full `uv run pytest`. EI source packages live directly under `ei/`; private external package source lives under `ei/package/`. The installed wheel and private modules use the bundle's `pkg` directory. Save complete verification output under ignored `data/test/<run-id>/`.

<a id="arm64-build"></a>

## EOS build and ARM64 setup

From the repository root, run `cargo build -p aether-runtime --bins -p aether-server` and `cargo test -p aether-runtime --bin aether-profile --bin aether-runtime --test arm_activation`. IsOS uses the `aether-profile` owner socket for setup and its sibling `aether-runtime` binary for the worker. On ARM64, build the Rust workspace with a supported Rust toolchain and the platform C/C++ compiler required by the CXX hardware adapter boundary. The runtime executables are `aether-runtime`, `aether-profile`, `aether-server`; IsOS launches them as private owner programs. Use `isos tui` to inspect the applied deployment. Physical adapters need hardware integration tests for typed samples, health, command bounds, cancellation, and Stop before deployment.

<a id="configure-eos"></a>

## EOS adapters and skills

For an EOS package adapter, select its exact pin, declared resource IDs, and owner-provided options in the IsOS graph. EOS validates the selected family, device identity, command ports, and Stop capability through the same [hardware interface](../../eos/interfaces/node/hardware/mock.md#hardware_mock) used by built-in adapters. IsOS renders the EOS-only projection at Apply; EOS reads the applied graph without modifying it. For a Rust skill, build a `.skill` executable with `aether_skill::Skill`, include it in a verified package, and select it through the EOS process node's `settings.skill_executables`. IsOS checks exact bytes; EOS runs a confined worker and brokers primitive calls through Dispatcher. See [Rust skill authoring](../../eos/core/skills/host-rust.md).

## EOS inspection, failure, and Stop

Start with `./isos.sh status --json` and the active graph revision. EOS has one persistent `aether-profile` owner and one `aether-runtime` arm worker for the starter graph. IsOS reads `data/eos/log/<deployment>/eos.jsonl` for its log panel; use the companion `eos.log` for direct reading. standalone EOS uses `data/eos/log/local/eos.jsonl`, and absolute `EOS_LOG_DIR` selects another directory. Owner replies carry Run, Status, activation, and Stop results. Each JSONL record has a UTC `timestamp`, lowercase `level`, `source`, and `message`; sources include `eos.aether_profile.owner@aether-v0.2.3`, `eos.aether_runtime.worker@aether-v0.2.3`, and `eos.hardware.mock.arm@aether-v0.2.3`. Compare status and logs for the same run; one log record does not prove readiness.

When **Activate** fails, compare its event ID and run revision with owner status. A stale identity is rejected before movement. `invalid_eos_graph` means the projection lacks the required chain or edge; `joint_limit` means the next delta exceeds the mock arm's configured limit or ±3.14 rad; `outcome_unknown` means the worker may have acted, so do not retry automatically with a new event ID. A successful result returns six mock joint positions in radians. Distinct accepted activations accumulate the small delta; repeating one event ID does not move the arm again. EI refreshes the arm observation independently of UI readers and carries freshness, health, and positions through the return path. The [arm control](../../eos/interfaces.md#arm_control) and [arm monitor](../../eos/interfaces.md#arm_monitor) contracts own exact values.

Use `isos deployment stop` for the ordinary managed Stop, then inspect `isos status --json`. EOS closes admission, waits for worker exit, and reports terminal evidence for the matching run ID and revision; a failed child is still reaped. Timeout, disconnect, cancellation, or an unconfirmed Stop leaves the physical outcome unknown until EOS reports a terminal result. Run again only after the prior owner run stops. `isos stop` is the separate workspace emergency-stop command. The mock arm has no physical hardware connection.
