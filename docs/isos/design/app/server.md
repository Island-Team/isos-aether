# Server and launcher design

This page explains the current source boundaries for contributors. The [HTTP contracts](../../interfaces/http/README.md) and [owner contracts](../../interfaces/manager/README.md) define public fields; [verification](../verification.md) records checks.

```text
src/
  main.rs               starts the application
  app/                  CLI, local HTTP, UI bundle
    server/routes/       HTTP handlers by domain
  domain/               graph, registry, packages, launch decisions
  runtime/              manager IPC, children, owner exchanges, logs
  interfaces/           typed boundary values
```

`app` admits local requests and parses them, then delegates decisions to `domain` and live operations to `runtime`. `domain` verifies exact pins and registered declarations without owning processes. `runtime` serializes manager mutations, supervises only IsOS-owned direct children, and retains run and stop state. `interfaces` holds exchanged values rather than a second state store. This split keeps package verification and revision checks out of transport handlers and maps typed errors once at the HTTP boundary.

The current Start/Restart wrapper contains a saved revision, ordered process specifications, resolved inputs, and ownership mode. The supervisor creates and binds the run ID; readiness and stop remain runtime responsibilities. The sections below explain package admission and output selection; a fully consolidated admission plan is still [open](../remaining-work.md).

The root `isos.sh` chooses `dev` or `product` before entering the Rust CLI. In `dev`, it selects this checkout's debug binary, EOS programs, EI programs, UI build, configuration, and portable home; `ISOS_HOME` changes the home while explicit configuration variables change their selected files. In `product`, it invokes the installed launcher under the configured prefix and selects checkout configuration and home unless explicitly overridden. The direct installed launcher detects a checkout from its current working directory when no home was selected. See [installation](installer.md) for operator commands.

The CLI entry point loads runtime configuration and paths before dispatch. Bare `isos`, `web`, and `tui` ensure setup and reuse or auto-start a server. `run` starts a foreground server and deployment only when no manager IPC exists; otherwise it asks the existing manager to start the deployment. `serve` starts the control plane and idle owner catalog services without starting EI or EOS deployment workers. `start` requires a running manager.

Before reusing a server, the CLI checks loopback HTTP health, service and API schema, then obtains manager identity over the selected owner-only Unix socket and compares its API origin. Development mode also compares the executable path and SHA-256, so a rebuilt local binary cannot silently reuse a stale manager. When no server is healthy, the CLI refuses an active orphaned manager socket, launches the current executable as a detached `serve` child, captures its output, and waits for both HTTP health and manager IPC up to the configured startup timeout. A startup timeout is a failed readiness observation; it does not prove that the child exited.

Foreground `serve` prepares paths and a default graph, verifies the active IsOS executable, starts idle owner services, and binds separate loopback UI and API listeners plus manager IPC. A missing or incompatible UI bundle leaves API and manager available. Readiness requires the UI listener when available and both API and manager listeners before the workbench reports ready. The server then monitors its threads and owner services until interrupt or failure; Stop is coordinated by the manager and owner proof. See the [manager IPC](../../interfaces/manager/protocol.md), [HTTP routes](../../interfaces/http/README.md), and [dependent Stop](../../interfaces/core/dependent-stop.md) contracts.

The graph pool is the only store of editable graph bytes. A deployment binding under `config/deployments/` contains just a pool name; `Paths::node_graph_path` resolves that binding for runtime and generated-revision checks. An older deployment graph is migrated at path preparation under a migration lock: exact-byte copies bind the existing demo, while differing bytes are imported to a unique pool file before the old file is removed. Apply reads a named pool file under the graph lock, checks its exact revision, validates it, publishes generated configuration, then updates the binding. Saving a bound pool file changes its saved revision; readiness reports `pending_apply` and Run stays fenced until Apply. A malformed binding or missing file never silently selects a different graph. The [graph API](../../interfaces/http/graph.md) defines the client request and errors.
